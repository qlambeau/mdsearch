# Architecture Decision Record

## Context

Status must distinguish unbuilt, current, and stale indexes using stored
collection content, without scanning sources or changing the database. Graph
and semantic state already record file-set fingerprints. Lexical state records
only passage count and build time; a timestamp or equal count cannot establish
freshness, especially for legacy databases.

## Decision

Read collection content and index state from a consistent SQLite read snapshot.
For lexical freshness, derive expected passages with the same domain
segmentation used by indexing and compare the complete persisted passage and
mapping set: file identity, passage kind, logical position, text, and byte
offset where that column exists. Compare recorded passage counts as well.
Missing, extra, or different indexed passages make a built lexical index stale.
Compare the columns supported by the database's schema version, without
requiring a legacy database to migrate during inspection.

For graph and semantic freshness, compare their recorded fingerprints with
the fingerprint derived from current stored file paths and content. Check
semantic model/dimension compatibility separately when determining readiness.
No state row means never built, with no successful-build timestamp. A stale
index retains its last successful build metadata. Disabled semantic indexing
is reported separately from an enabled index that has not been built; residual
state remains visible until the next update performs the approved cleanup.

Do not persist inferred fingerprints, change build times, migrate schema, scan
source paths, or load/download models during status. Schema version remains 9.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Add a lexical fingerprint column and backfill it from current files | Backfilling can falsely certify an already-stale legacy index |
| Add a nullable fingerprint and mark every legacy index stale | Creates migration and rebuild requirements for indexes that may already match stored content |
| Compare only counts or timestamps | Equal counts and timestamps cannot establish content equality |
| Scan sources to detect pending filesystem edits | Contradicts the approved stored-content freshness boundary |

## Consequences

### Positive

- Accurate lexical inspection works with existing and legacy index rows.
- Inspection does not mutate data or require source access.
- Existing graph and semantic state remain the durable build records.
- No dependency, table, or schema migration is added.

### Negative Or Tradeoffs

- Lexical inspection reads and segments stored content on every invocation;
  cost grows with stored bytes and indexed passages.
- Comparison must use indexing's deterministic segmentation and handle legacy
  columns explicitly to avoid false stale reports.
- Lexical freshness describes the represented passage content: an edit that
  does not change any indexed passage or mapping does not make that index stale.

## Follow-Up Actions

- Implement snapshot-based read-only status within the existing SQLite adapter.
- Test built/unbuilt, stale text with equal counts, missing/extra mappings,
  empty collections, legacy schemas, and retained successful-build metadata.
- Test status after filesystem edits or source removal without accessing sources.
