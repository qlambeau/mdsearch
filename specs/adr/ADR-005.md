# Architecture Decision Record

## Context

EPIC-003 builds a per-passage lexical index during `collection update`. The
index must cover the recognized frontmatter fields (`title`, `tags`, `aliases`,
`summary`) alongside the body, with frontmatter treated as optional and lenient:
malformed frontmatter is indexed body-only, reported, and never fails the
update. Extracting those fields from a leading YAML block introduces a parsing
dependency decision.

Separately, the lexical index is ranked with BM25 (ADR-001). BM25's IDF and
length-normalization statistics are computed over the whole indexed corpus, and
its scores are only comparable across queries when that corpus is static. The
PRD ranks search-result quality as the top priority and treats index build time
as unconstrained, at a scale of 100 to 5,000 documents per collection.

## Decision

- Add the pure-Rust `yaml-rust2` crate to the `domain` layer for lenient YAML
  frontmatter parsing. It is `no_std`-friendly, contains no `unsafe`, is
  MIT/Apache-2.0 licensed (within the repository's license allow-list), is
  actively maintained, and introduces no I/O or framework dependency into the
  domain layer, satisfying `R-DIR-02`.
- Rebuild the entire lexical index for a collection on every `collection
  update` (delete all of its indexed passages and reinsert them from the
  reconciled file set) inside the same transaction as the file changes, instead
  of incrementally patching the index.

The full rebuild keeps the indexed corpus static per update, which keeps BM25
statistics stable and comparable, and it guarantees the index always reflects
the reconciled file set exactly. It is deliberately coupled to the explicit
update command per the PRD constraint that indexing is driven by explicit update
commands.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| `serde_yaml` / `serde_yml` | `serde_yaml` is in maintenance mode; both pull a heavier serde stack for four scalar fields |
| Hand-rolled frontmatter parser | Fragile against YAML variance and violates the `std`-first dependency bar (`R-DEP-01`); lenient failure semantics would be ad hoc |
| Incremental index patching on update | Higher complexity, partial-state risk, and unstable BM25 statistics from a changing corpus |
| Per-file FTS5 tables | Index-table-per-file does not scale and complicates collection-wide statistics |
| Application-side BM25 ranking instead of FTS5 `bm25()` | Duplicates a capability the selected engine already provides (ADR-001) |

## Consequences

### Positive

- The domain layer gains a pure, safe parser that supports lenient extraction of
  the four recognized fields.
- Full rebuild is simple, deterministic, and trivially verifiable against the
  reconciled file set.
- Atomicity between file changes and the index is naturally preserved in one
  SQLite transaction.
- BM25 statistics are computed over a static corpus per update, keeping scores
  stable and comparable.
- The mapping of passages back to files (`passage_files`) is independent of the
  FTS5 rebuild, so future retrieval slices can reuse it.

### Negative Or Tradeoffs

- A full rebuild is O(collection size) per update; acceptable because indexing
  time is unconstrained per the PRD and the collection scale is bounded.
- `yaml-rust2` adds a small dependency tree to the domain layer; it is pure and
  license-clean but must be kept current through the normal dependency process.
- Lenient parsing means some malformed frontmatter is silently treated as body
  text; the tradeoff (never failing an update) is the approved behavior.

## Follow-Up Actions

- Confine YAML parsing to the domain `passage` module so the rest of the
  workspace depends on the parsed result, never on the parser.
- Property-test passage segmentation, including malformed and absent frontmatter,
  and commit failing seeds as regression cases.
- Run `cargo deny check` after adding the dependency to confirm the license and
  advisory gates.
- Update `DB-001` and the table specifications for the new index tables before
  implementing the schema migration.
