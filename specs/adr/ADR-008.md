# Architecture Decision Record

## Context

EPIC-005 adds the contextual entity index: `mdsearch update` deterministically
builds an entity graph for each collection (file, tag, and alias nodes with
typed, directional edges) in the same SQLite database. Two consequential
decisions need resolution:

1. How are the graph nodes/edges stored and traversed in the single embedded
   SQLite file, given the existing FTS5 lexical and vector indexes?
2. `ADR-001`/`DEC-009` selected `async-graphql` as the internal in-process
   context-query layer, but that crate is **not yet a workspace dependency**.
   Does this slice add it, and how is the query layer exposed without a server?

## Decision

1. **Store the graph in plain SQLite `nodes` and `edges` tables and traverse with
   recursive CTEs.** `nodes` holds one row per node (file, tag, or alias) with a
   stable identity; `edges` holds typed, directional edges with a
   `UNIQUE (src_id, dst_id, relation)` constraint for idempotent loads. A
   per-collection `graph_state` table mirrors the existing state-table pattern
   (fingerprint, node/edge counts, build timestamp). This keeps the graph in the
   same file as lexical and semantic indexes, with no new storage engine, and
   recursive-CTE traversal is sub-millisecond at the PRD's 100-5,000 document
   scale.

2. **Add `async-graphql` as a workspace dependency and build the internal query
   layer with it now** (explicit human approval given in this session per
   `R-AGT-02`). The layer is in-process only: typed GraphQL resolvers run over
   the `GraphStore` port and are invoked by the debug CLI and later slices; no
   GraphQL server is exposed and the CLI-only product boundary is unchanged
   (DEC-009). The graph itself lives in SQLite and is traversed with recursive
   CTEs; async-graphql is the typed query/API surface on top, not the graph
   engine.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| A dedicated graph database (e.g. Kùzu, Neo4j) or separate graph file | Violates the one-database-file constraint and adds a server/engine component; recursive CTEs suffice at this scale |
| LLM claim extraction (`DEPENDS_ON`-style typed claims) | Rejected in the story: this slice is a deterministic structure graph with zero LLM cost; claim extraction is a future slice |
| A standalone `mdsearch graph` build command | Rejected in the story: graph build folds into `mdsearch update` alongside the lexical index |
| Incremental UPSERT + tombstone graph maintenance | Rejected in the story: `update` fully rebuilds the graph deterministically each run, matching the ADR-005 lexical precedent |
| Defer `async-graphql` and expose a plain port/recursive-CTE API only | The user chose to add `async-graphql` now to honor ADR-001/DEC-009; it is the documented internal context-query layer |
| Key graph nodes to physical file rowids | File nodes use the stable indexing-assigned file ID (US-006); physical rowids change on rebuild |

## Consequences

### Positive

- The graph lives in the same SQLite file as all other indexes, satisfying the
  one-database-file constraint.
- Full deterministic rebuild on `update` removes stale nodes/edges automatically
  and stays idempotent, consistent with ADR-005.
- `async-graphql` provides a typed, Rust-native query surface over the graph for
  the debug CLI and future EPIC-006 retrieval, without exposing a server.
- Node/edge `UNIQUE` constraints make the rebuild free of duplicates.

### Negative Or Tradeoffs

- `async-graphql` adds a dependency tree; its license and advisory gates are
  validated before merge, and its features are trimmed to the in-process use
  (no server/subscription features unless needed).
- Recursive-CTE traversal, while fast at this scale, would degrade for
  arbitrary-depth or complex pattern queries; an embedded engine is the
  documented upgrade path only if that becomes limiting.
- The graph is structure-derived; it does not capture claim-level relationships
  (`DEPENDS_ON`), which remain out of scope for this slice.
- `nodes`/`edges` tables must stay in sync with the frontmatter vocabulary; a
  new frontmatter field implies a migration.
