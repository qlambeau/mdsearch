# Architecture Decision Record

## Context

The Rust Engineering Constitution (`specs/CONSTITUTION.md`) did not contain an explicit normative rule for database table schema primary keys across database engines. Without a binding rule, different database adapters and migrations could use natural keys, inconsistent primary key column names (such as `collection_id`, `node_id`, or `key`), or composite keys as primary identifiers.

In spec-driven and domain-driven design, decoupling physical persistence identifiers from domain-specific attributes ensures uniform record identification, simplifies generic relational and persistence operations, avoids schema cascading issues when domain identifiers change, and guarantees consistent primary key naming across all tables and databases.

The current-session human explicitly authorized an amendment to the constitution to establish a mandatory rule for database table primary keys.

## Decision

Amend `specs/CONSTITUTION.md` by adding rule `R-DB-01` under a new subsection `### 4.3 Database and persistence schemas`:

- **R-DB-01** — When creating a table schema for a database, regardless of the database technology, every table MUST have a domain-independent primary key named `id` with a unique identifier enforced by the database system, if supported.

Key tenets of this rule:
1. **Universality**: Applies to all table schemas created for any database engine used in the repository (e.g., SQLite, PostgreSQL, etc.).
2. **Standard naming**: The primary key column MUST be named `id`.
3. **Domain independence**: The primary key MUST be surrogate/synthetic (domain-independent) rather than a natural or domain-specific key. Domain uniqueness (such as unique paths, names, or codes) MUST be enforced through separate `UNIQUE` constraints/indexes rather than the primary key.
4. **Database enforcement**: The unique identifier generation and uniqueness constraint MUST be enforced by the database system itself (e.g. `INTEGER PRIMARY KEY AUTOINCREMENT` / rowid alias in SQLite, `BIGSERIAL` / `IDENTITY` / `gen_random_uuid()` in Postgres), wherever supported by the database engine.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Use domain-specific primary key names (e.g., `collection_id`, `file_id`) | Creates inconsistent column naming across tables, complicates reusable queries, and tightly couples persistence identity to table-specific domain terms. |
| Use natural primary keys (e.g., `path`, `key`, `name`) | Fragile when domain identifiers are renamed or updated, requires cascading foreign key updates, and degrades join performance. |
| Leave as a non-normative guideline or convention | Fails to prevent schema inconsistencies across agent-generated and human-written migrations. |

## Consequences

### Positive

- Standardized schema design across all tables and databases in the codebase.
- Consistent `id` primary key column name across all entity records, simplifying repository abstractions and tooling.
- Database engine enforces identifier uniqueness and generation reliably.
- Domain attributes (names, paths, slugs) can change without mutating primary key relationships or foreign keys.

### Negative Or Tradeoffs

- Existing tables authored before this rule will need migration or compatibility considerations if refactored.
- Compound or natural keys cannot serve directly as the primary key; they require a surrogate `id` plus a secondary unique constraint.

## Follow-Up Actions

- Update `specs/CONSTITUTION.md` with rule `R-DB-01`.
- Ensure all future table definitions (`TABLE-NNN` artifacts, migration scripts, and adapter DDL) comply with `R-DB-01`.
- Review existing table schemas in upcoming refactor slices to migrate legacy primary key conventions to `id`.
