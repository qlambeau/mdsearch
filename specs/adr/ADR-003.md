# Architecture Decision Record

## Context

The approved database decision uses `sqlite-vector-rs` 0.3.1 for semantic vector
storage and HNSW search. Its published `register` API loads a companion shared
library, which conflicts with the product requirement for one compiled binary.

Static registration requires integrating the extension's SQLite virtual-table
implementation into the binary. The extension contains reviewed FFI and
low-level SQLite code that cannot satisfy the repository's ordinary
`forbid(unsafe_code)` rule without an explicit exception.

## Decision

Vendor `sqlite-vector-rs` as a dedicated SQLite adapter implementation and
statically integrate it into the `mdsearch` binary.

- Keep all extension-specific unsafe code inside the dedicated SQLite adapter boundary.
- Expose only a safe registration and vector-storage API to the rest of the workspace.
- Do not add unsafe code to the domain, application, infrastructure, or CLI crates.
- Preserve the single-binary and offline constraints; do not require a companion shared library at runtime.
- Retain the upstream license and attribution in the vendored source.
- Add safety comments and tests for every unsafe boundary introduced or modified by the integration.

This ADR is the human-reviewed authorization required by the constitution for
the vendored FFI boundary and the exception to the ordinary no-unsafe rule.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Load the published companion shared library | Violates the single compiled binary constraint |
| Defer vector integration to EPIC-004 | Would leave the approved database foundation unvalidated and postpone a known packaging constraint |
| Replace `sqlite-vector-rs` with `sqlite-vec` | Not the selected vector extension and would require a new technical decision |
| Reimplement vector indexing in application Rust | Duplicates the selected extension and risks lower search quality and performance |

## Consequences

### Positive

- The final binary remains self-contained and offline-capable.
- Vector storage and HNSW search remain in the selected SQLite engine.
- Unsafe code is isolated at one technology boundary with an explicit review record.
- The application and domain layers remain safe and independent of SQLite internals.

### Negative Or Tradeoffs

- Vendored upstream code must be reviewed and updated deliberately rather than through an ordinary version bump.
- SQLite and extension build compatibility becomes part of the workspace build.
- The adapter must maintain safety invariants across the SQLite C boundary.
- Extension upgrades require regression tests and a new review of the unsafe boundary.
- Vendored upstream source is excluded from `mdsearch`'s project coverage threshold,
  while its compiled tests and the adapter's vector smoke test still execute.
- The selected `sqlite3_ext` dependency brings the `blessing` license and an
  unmaintained transitive `paste` crate; the latter is accepted under
  `RUSTSEC-2024-0436` because no safe upgrade is currently available.
- Duplicate transitive versions are accepted because the selected SQLite
  bridge and vector stack require incompatible but link-safe dependency lines.

## Follow-Up Actions

- Preserve the smallest upstream source patch that exposes static registration safely.
- Keep the exact `sqlite-vector-rs` 0.3.1 source under `vendor/sqlite-vector-rs/` with its MIT OR Apache-2.0 license metadata.
- Add adapter-level smoke tests for registration, vector table creation, insert, and nearest-neighbor query.
- Run the full constitution gates and record observed output after integration.
