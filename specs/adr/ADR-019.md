# Architecture Decision Record

## Context

The existing GraphQL layer accepts collection names independently on node and
neighbor fields. The CLI also accepts a collection but does not impose it on
resolvers. A query can therefore return another collection's graph, including
through multiple roots or aliases. The approved breaking CLI makes collection
selection an invocation-wide boundary.

## Decision

Validate the selected collection before executing a query and inject its typed
CollectionName into the in-process async-graphql context. Remove collection
arguments from every public graph field. All resolvers obtain scope from the
context and pass that same scope to GraphStore lookups and traversals.
Unsupported collection arguments fail normal GraphQL validation before data
resolution. Aliases and multiple roots cannot alter the context.

Keep the existing internal schema and GraphStore port. The query root owns a
concrete generic store behind synchronization required by async-graphql; do
not introduce an Arc<Mutex<dyn Port>> handle. Hold the synchronous store lock
only while reading, never across an await. No server, dependency, storage
layer, or graph algorithm is added.

Neighbor CLI inspection uses the same typed collection boundary, with explicit
node kind, relation filter, and bounded depth rather than guessing node kind.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Retain field collection arguments and check equality | Duplicates scope and leaves a confusing public API with arguments that cannot vary |
| Rewrite query strings to inject the collection | Fragile for variables, aliases, fragments, and multiple roots |
| Filter results after resolving unrestricted queries | Reads the wrong scope and cannot reliably undo leakage through nested results |
| Replace GraphQL with a new query language | Unnecessary and conflicts with preservation of the established internal query layer |

## Consequences

### Positive

- Every field and traversal shares the invocation's collection boundary.
- Query validation rejects attempts to override scope.
- CLI and schema no longer duplicate collection arguments.
- Typed store ownership respects constitutional port rules.

### Negative Or Tradeoffs

- Existing query documents must remove collection arguments.
- Schema construction and tests must supply the selected typed collection.
- The synchronous SQLite store remains serialized during each resolver read.

## Follow-Up Actions

- Change schema construction and node/neighbor resolvers together.
- Test same-key graphs in different collections, aliases, multiple roots, and
  attempted scope overrides on every public field.
- Publish replacement graph-query examples and the old-to-new command mapping.
