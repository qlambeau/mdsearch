# Architecture Decision Record

## Context

EPIC-004 adds a semantic (vector) index and hybrid search in two slices. The
first slice (`US-010`) built the semantic index with `mdsearch embed`. The
second slice (`US-011`) adds the `mdsearch hybrid QUERY` command that fuses
lexical (BM25) and semantic (cosine) results into one ranked list and then
re-ranks the fused list with a local cross-encoder model.

Three consequential decisions needed resolution:

1. Which fusion algorithm combines the heterogeneous lexical and semantic
   scores into one ranking?
2. Which local cross-encoder model re-ranks the fused pool, and can it be
   hosted by an already-approved dependency?
3. How are the re-ranker model assets provisioned locally under the
   offline-by-default constraint, given that hybrid search is read-only and
   never performs network I/O?

## Decision

1. **Fuse with Reciprocal Rank Fusion (RRF)** with the standard constant
   `k = 60` and a per-leg oversample candidate pool of `3 x --limit`. RRF is a
   rank-based fusion that combines the positions of each candidate in the
   lexical and semantic ranked lists as `1 / (k + rank)` per list. It requires
   no score calibration between BM25 and cosine similarity, is the established
   hybrid-search default, and its `k` and oversample factor are tunable
   constants validated later through the ADR-004 evaluation framework.

2. **Default re-ranker `BAAI/bge-reranker-base`, hosted by `fastembed`
   6.0.0's `TextRerank`.** No new dependency is required: the already-approved
   `fastembed` crate (ADR-006) ships a cross-encoder re-ranker
   (`fastembed::TextRerank`) with `bge-reranker-base` as its own default. The
   supported re-ranker set is fastembed's `RerankerModel` set. The re-ranker is
   a second stage after RRF fusion: the whole fused candidate pool is re-scored,
   ordered by the re-ranker score, and cut to `--limit`.

3. **Provision the re-ranker through `mdsearch embed --reranker NAME
   --download` and record a global `reranker_model` setting** in the existing
   `settings` table (no migration, no stored vectors). The re-ranker is a
   cache entry plus a setting, not an index. `mdsearch hybrid` is read-only and
   reads the cache; if the re-ranker assets are absent and re-ranking is on
   (the default), it falls back to RRF-only ordering for that run with a
   warning, and `--no-rerank` disables the stage entirely.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Weighted normalized-score fusion (e.g., `0.5 x BM25 + 0.5 x cosine`) | Requires calibrating two heterogeneous score scales per collection; fragile across collections and models. RRF is scale-free and robust |
| RRF with exposed weights or a `--candidates` flag now | The user chose an oversampled-then-cut pool with fixed internals; weights and pool size are tuned later through ADR-004 rather than exposed prematurely |
| A different cross-encoder default (`jina-reranker-v1-turbo-en`, `bge-reranker-v2-m3`) | User selected `bge-reranker-base`, fastembed's default; it covers English and Chinese and is revisited through ADR-004 evaluation |
| Add a new dependency for re-ranking | Unnecessary: `fastembed` 6.0.0 already provides `TextRerank`; a new dependency would trigger the constitution's approval gate for no benefit |
| Fetch re-ranker assets via `hybrid --download` | Hybrid search is read-only by contract (REQ-011 postconditions); provisioning through `embed` keeps model-asset writes in the one command that owns them |
| Store re-ranker vectors in the database | The re-ranker is a cross-encoder applied at query time; persisting its output is meaningless. It is a cache entry plus a recorded setting |
| Require the re-ranker to be cached or fail | User chose graceful degradation: an uncached re-ranker falls back to RRF-only with a warning, keeping hybrid usable out of the box |

## Consequences

### Positive

- RRF needs no score calibration, so the fused ranking is stable across
  collections and models and easy to reason about.
- `bge-reranker-base` through `fastembed` requires no new dependency or new
  workspace member, preserving the constitution's dependency discipline.
- Provisioning through `embed` keeps hybrid search read-only and fully offline;
  a missing re-ranker degrades gracefully instead of blocking search.
- The global `reranker_model` setting lives in the existing `settings` table;
  no migration and no schema change.
- ADR-004 can tune `k`, the oversample factor, and the re-ranker model
  empirically against the golden dataset.

### Negative Or Tradeoffs

- Re-ranking is cross-encoder inference at query time and is the dominant
  latency cost; the oversample pool (3 x limit) bounds it, but harness
  context-filling latency must be measured against the PRD soft target.
- `bge-reranker-base` assets are large and must be provisioned locally; users
  who never run `embed --reranker --download` get RRF-only results with a
  warning.
- The re-ranker score (a relevance logit) is not directly comparable with the
  fused RRF score; the human output shows the ordering score, and `--json`
  exposes both.
- Adding `--reranker` to `embed` revises the already-implemented embed contract
  (REQ-010, DES-010), which this slice updates rather than silently extending.

## Follow-Up Actions

- Update `REQ-010` and `DES-010` to record the `embed --reranker` extension and
  the `reranker_model` setting before implementation.
- Verify the vendored `sqlite-vector` `knn_match` distance-to-similarity sign
  for the cosine metric before the semantic leg is complete.
- Map the friendly re-ranker name `bge-reranker-base` to
  `fastembed::RerankerModel::BGERerankerBase` in the `embed-fastembed` adapter,
  mirroring the embedding friendly-name mapping.
- Validate the free-text-to-FTS5 mapper quotes FTS5 operator characters so
  `AND`, `OR`, quotes, and `prefix*` are treated as literal text.
- Run the ADR-004 evaluation framework once hybrid search lands to confirm the
  RRF `k = 60` and `3 x limit` oversample defaults and the re-ranker model.
