# Architecture Decision Record

## Context

The semantic index is pinned to 384 dimensions: the `embeddings` virtual table
is created with `dim=384`, a compile-time constant guards every insert, and
advertised 1024-dimension models fail at the first rebuild with a confusing
storage-level mismatch (OBS-002). The approved product decision (DEC-014 in
`PRD-001`) requires every supported fastembed model to embed and search
successfully, with the model and dimension recorded per collection and
validated on reads.

sqlite-vector virtual tables fix one dimension for the whole table, so storing
collections at different dimensions requires a physical layout decision: one
shared table per dimension, one table per collection, or one shared table at
the active model's dimension.

## Decision

Use **one shared `embeddings` table at the active model's dimension**. The
active dimension is recorded in the `settings` table (`embedding_dimension`
key) when the vector table is created; absent means 384 (legacy). When a model
switch changes the active dimension, the embed flow drops the `embeddings`
table, recreates it at the new dimension, and rebuilds every embedded
collection into it (REQ-010 FR-007 semantics), committing the settings write
with the table recreation. Each collection's `semantic_index_state` row records
the model and dimension that built its vectors; the `hybrid` semantic leg
validates the recorded dimension against the active dimension before returning
results. All collections therefore share one active dimension at a time, and
mixed-dimension coexistence is explicitly out of scope.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| One vector table per dimension (`embeddings_384`, `embeddings_1024`, ...) | No user value from mixed-dimension coexistence; adds table naming, per-dimension query routing, and cleanup complexity for a capability nothing in the product needs |
| One vector table per collection | Table explosion at PRD scale (5,000 docs/collection) and complicates the global model switch, which rebuilds every collection anyway |
| Keep a fixed 384 dimension and reject other models | Contradicts the approved DEC-014 decision that advertised models must work |

## Consequences

### Positive

- Every supported model (including 1024-dimension models) embeds and searches
  without a dimension error.
- One schema surface: no per-dimension or per-collection table management; the
  global model switch path already rebuilds all collections.
- Deterministic read validation: recorded state dimension vs. recorded active
  dimension, both explicit integers in the database.
- Legacy 384-dimension databases need no migration or rebuild.

### Negative Or Tradeoffs

- Collections cannot coexist at different dimensions; switching models is a
  database-wide operation (it already was, via REQ-010 FR-007).
- A model switch is a destructive table recreation; it is safe only because it
  happens exactly when every embedded collection is rebuilt, and the settings
  write commits with the recreation.
- The active dimension must be derived from the model at table creation; the
  model-to-dimension mapping lives in the embed adapter and needs integration
  tests per supported model.

## Follow-Up Actions

- Record `embedding_dimension` in `settings` at vector-table creation; infer
  384 when absent.
- Add `dimension` to `semantic_index_state` (additive migration, schema-version
  bump); write it at rebuild; read legacy NULL as 384.
- Validate recorded dimensions on the `hybrid` semantic leg before results.
- Report the recorded model and dimension in `mdsearch index status`.
- Revise `REQ-010`, `REQ-011`, `REQ-006`, `TABLE-007`, `TABLE-008`,
  `TABLE-009`, and `DB-001` in the same change set (R-SDD-05).
