# Architecture Decision Record

## Context

`mdsearch search` and `mdsearch hybrid` interpreted the same query string
differently (OBS-001): the lexical path submitted raw FTS5 syntax (so `AND`,
`OR`, quotes, and `prefix*` acted as operators, and a malformed expression
failed via a fragile `message.contains("fts5")` heuristic — OBS-003), while the
hybrid path neutralized the query through the domain mapper `free_text_to_fts5`
(`crates/domain/src/fusion.rs:132`). The approved product decision (DEC-013 in
`PRD-001`) makes literal free text the semantics on both commands, and `REQ-014`
FR-006 requires `InvalidQuery` classification to be deterministic and
independent of engine error-message text while remaining defense-in-depth.

Two design questions had to be settled: where the neutralization applies on the
lexical path, and how query-error classification becomes deterministic given
that FTS5 syntax errors surface as generic `SQLITE_ERROR` with no distinct
extended result code.

## Decision

1. **The application use case owns query interpretation.** `SearchLexical::execute`
   applies the existing domain mapper `free_text_to_fts5` before calling the
   store, mirroring `HybridSearch::execute`. The domain mapper is the single
   source of truth for query-to-FTS5 mapping on both commands; the port
   signature, the CLI, and the adapter stay unchanged.

2. **Error classification is validation-by-construction.** The neutralizer's
   output is guaranteed syntactically valid FTS5 — every term is a quoted
   phrase, embedded quotes are doubled, terms are `AND`-joined — so the store's
   `search_query_failure` no longer matches on engine message text; query-path
   execution failures map to `SearchStoreError::Storage`. The `InvalidQuery`
   variants in `SearchStoreError` and `SearchError` remain in the public error
   enums as defense-in-depth and are unreachable for normal user input.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Neutralize inside the SQLite adapter | Puts query semantics in the adapter (R-SEP-04) and diverges from the hybrid use case, which already neutralizes in `application` |
| Keep classification with a tighter `"fts5:"` message prefix | Still dependent on engine message text; fails FR-006's determinism requirement |
| Classify via rusqlite error variant or SQLite extended result code | FTS5 syntax errors carry no distinct extended code; they cannot be distinguished from storage failures by code alone |
| Pre-validate the query structurally in the store | Redundant with the neutralizer's validity-by-construction guarantee; a second validation site invites drift |
| Neutralize in the CLI composition layer | Composition must not own domain logic; the use case is the correct boundary |

## Consequences

### Positive

- The identical query string now produces the identical matching passages on
  both commands, which simplifies documentation, harness callers, and ADR-004
  evaluation comparisons.
- Error classification is deterministic and independent of SQLite message
  wording or error-code evolution.
- The domain-owned neutralizer is the single source of truth, with its existing
  unit and property tests covering the mapping.
- No schema change, no migration, no new dependency, and no port or CLI change.

### Negative Or Tradeoffs

- `InvalidQuery` becomes effectively unreachable API surface, retained only as
  defense-in-depth per the approved contract; raw store-level callers lose
  malformed-query classification.
- The existing store test asserting malformed-query classification must be
  replaced (behavior change, R-SDD-05).
- Search results for queries containing operator characters may change (the
  intended behavior), which can shift golden evaluation scores and require a
  re-baselined ADR-004 dataset.

## Follow-Up Actions

- Implement the neutralization in `SearchLexical::execute` and revise
  `search_query_failure` in `crates/adapters/store-sqlite`.
- Replace the store's `reports_a_malformed_query` test with regression tests
  for literal operator semantics and deterministic storage mapping.
- Add a property-style domain test that neutralized arbitrary free text never
  produces an FTS5 query error.
- Re-run `cargo xtask eval`; update the recorded baseline only if scores shift
  and the ADR-004 targets still hold.
