# Architecture Decision Record

## Context

US-022 makes semantic indexing an explicit per-collection choice. Existing
collections already have semantic-index state when they have been embedded,
but the database does not store whether semantic indexing is enabled for
future updates. A durable policy must also distinguish a deliberately disabled
collection from one whose semantic index has not yet been built.

## Decision

Add a constrained `semantic_enabled` property to the existing `collections`
table in schema version 9. The value is stored as an integer boolean, defaults
to false for newly created collections, and is included in collection
configuration persistence.

During migration, set `semantic_enabled` to true only for collections that
have a `semantic_index_state` row. Collections without such a row remain
disabled. The migration does not build, remove, or otherwise change file or
index data. Disabling the policy is persisted immediately; the next successful
collection update removes that collection's vectors and semantic-index state
in its transaction.

Update `TABLE-002` and `DB-001` to specify the field and schema-version-9
migration. No separate policy table is added.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Infer enablement from the presence of vectors or semantic-index state on every update | There is no durable way to record a user-requested disable state after the index is removed |
| Store the policy in a separate collection-settings table | Adds a table and join for one collection property, with extra deletion and migration handling |
| Default all legacy collections to disabled | Silently changes behavior for users who already maintain semantic indexes |
| Default all legacy collections to enabled | Creates semantic-index work for collections that have never opted into or built semantic indexing |

## Consequences

### Positive

- Semantic policy is explicit, queryable, and independent of index staleness.
- Existing semantic collections retain their behavior after migration.
- New collections remain lexical/graph-only unless the user opts in.
- Collection destruction continues to remove policy with the owning collection.

### Negative Or Tradeoffs

- The database requires a schema-version-9 migration and updates to the
  existing `collections` table specification.
- Policy and semantic-index state can differ after configuration changes until
  the next successful update; this is intentional and lets configuration
  remain free of indexing work.

## Follow-Up Actions

- Add the `semantic_enabled` definition and v9 migration to `TABLE-002` and
  `DB-001`.
- Test migration from schema versions 0–8, including both existing and absent
  semantic-index state.
- Test collection create/configure and destroy behavior with the persisted
  policy.
