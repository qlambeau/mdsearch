# Architecture Decision Record

## Context

EPIC-004 adds a semantic (vector) index and hybrid search in two slices. The
first slice (`US-010`) adds the dedicated `mdsearch embed` command that builds
and maintains the per-passage semantic index. Several consequential decisions
were already approved in the story and design interviews:

- Embedding is per-passage, aligned with the lexical passage set, with vectors
  keyed to the same logical passages the lexical index covers.
- `fastembed` is the embedding library (ADR-001) and `sqlite-vector` stores and
  searches vectors in the same SQLite file (ADR-001, ADR-003).
- The command is `mdsearch embed`, a separate explicit command; `update`
  remains lexical-only.
- A single global embedding model is recorded; a `--model` switch rebuilds every
  embedded collection.
- Model assets are provisioned locally; a missing model fails clearly unless
  `--download` is passed.

Two open technical questions remain unresolved until now:

1. Which local model is the default and the first supported entry, and how is
   the new `fastembed` crate-level dependency and adapter hosted (the
   constitution's `R-AGT-02` requires explicit human approval)?
2. The lexical index is fully rebuilt on every `update` (ADR-005), which
   destroys and recreates FTS5 passage rowids even when file content is
   unchanged. How should semantic vectors stay consistent with the lexical
   passages across such rebuilds?

## Decision

1. **Add `fastembed` as a workspace dependency** (explicit human approval given
   in this session) and host the embedding generator in a new adapter crate
   `crates/adapters/embed-fastembed` implementing the application
   `EmbeddingGenerator` port. This keeps embedding inference separate from
   SQLite storage, matching the adapter-per-technology layout, and keeps
   `fastembed` (which performs model I/O and inference) out of `domain` and
   `application`.

2. **Default model `all-MiniLM-L6-v2`** (384 dimensions, cosine metric). It is
   the default for `mdsearch embed` and the first entry in the supported set.
   Model choice is revisited through the ADR-004 evaluation framework rather
   than fixed forever; the CLI already exposes `--model`.

3. **Key semantic vectors to a stable logical passage identity
   `(file_id, kind, position)` instead of the physical FTS5 passage rowid.**
   The `embeddings` vector table stores these three metadata columns alongside
   each vector. This keeps vectors valid across no-op `update` runs (which
   re-segment and re-insert passages under new rowids) and lets hybrid search
   join semantic results back to the lexical `passage_files` rows by
   `(file_id, kind, position)`.

4. **Schema v5 migration** adds: a `settings` key/value table holding the
   global `embed_model`; a `semantic_index_state` table recording each
   collection's file-set fingerprint, model, passage count, and embed timestamp;
   and an `embeddings` vector virtual table with metadata columns
   `collection_id`, `file_id`, `kind`, and `position`.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Host `fastembed` inside the existing `store-sqlite` adapter | Mixes SQLite storage with model inference in one adapter, weakening the one-technology-per-adapter boundary |
| Host `fastembed` in the `infrastructure` crate | Infrastructure is for cross-cutting concerns; embedding is a dedicated technology adapter |
| Defer `fastembed` and build a port-only fake | ADR-001 already selected fastembed and the user approved the dependency now; a port-only slice would ship no real embedding capability |
| No default model; require `--model` always | A default keeps `embed` usable out of the box and is tuned later via ADR-004 |
| Key vectors to the physical FTS5 passage rowid | `update` rebuilds the lexical index every run, so rowids change even when content is unchanged; vectors would silently dangle (rejected in the design interview) |
| Add a rebuild trigger on every lexical rebuild to keep rowid keying | Rejected in the design interview: it would rebuild the semantic index on every no-op `update`; the stable logical key avoids extra rebuilds |
| Per-collection global model | Rejected in the story: a single global model guarantees database-wide vector comparability and a clean switch-and-rebuild |

## Consequences

### Positive

- The embedding adapter is isolated behind the `EmbeddingGenerator` port; model
  I/O and inference stay out of the pure layers.
- The default model gives a working offline embedding path immediately, with
  ADR-004 evaluation guiding future tuning.
- Logical passage keying keeps the semantic index consistent across lexical
  rebuilds without extra rebuilds or dangling vectors.
- Schema v5 keeps the global model and per-collection embed state in the same
  file, satisfying the one-database-file constraint.

### Negative Or Tradeoffs

- `fastembed` adds a significant dependency tree (model loading, tokenization,
  inference); its license and advisory gates are validated before merge.
- The `embed-fastembed` adapter is a new workspace member, adding a build unit
  and its own test surface.
- Vector search quality depends on the chosen model; the default is a starting
  point subject to ADR-004 measurement.
- The `(file_id, kind, position)` key is stable only while the stored file set
  is unchanged; `update` still changes passages when content changes, so
  staleness must be detected by the stored file-set fingerprint rather than by
  the passage rows themselves.
- The vector table's delete-and-reinsert rebuild path must be verified against
  the vendored `sqlite-vector` extension.

## Follow-Up Actions

- Add `fastembed` to `[workspace.dependencies]`, create
  `crates/adapters/embed-fastembed`, and wire it only in `crates/app`.
- Run `cargo deny check` after adding the dependency to confirm the license and
  advisory gates.
- Inspect fastembed's actual cache directory layout and align the availability
  check with it.
- Update `DB-001` and add table specifications for the schema-v5 tables before
  implementing the migration.
- Validate the vector-table predicate delete (`DELETE ... WHERE collection_id =
  ?`) with the vendored `sqlite-vector` extension before this slice is complete.
