# Architecture Decision Record

## Context

`destroy_collection` executes only `DELETE FROM collections WHERE name_key = ?1`
(`crates/adapters/store-sqlite/src/lib.rs:314`), leaving the collection's
files, FTS5 passages, mappings, vectors, graph rows, and index-state rows
orphaned permanently (OBS-008). SQLite does not enforce the declared
`ON DELETE CASCADE` clauses because `PRAGMA foreign_keys = ON` is never
executed on connection open, and the virtual tables (`passages` FTS5,
`embeddings` sqlite-vector) cannot declare foreign keys at all. Because
SQLite reuses rowids, a later collection can inherit the destroyed
collection's orphaned data. The approved product decision (DEC-015 in
`PRD-001`) requires complete, atomic cleanup.

## Decision

`destroy_collection` performs an **explicit per-table delete list in one
transaction**: resolve the `collection_id`, then delete the collection's rows
from `embeddings`, `passages` (by rowid subset), `passage_files`, `files`,
`edges`, `nodes`, `graph_state`, `lexical_index_state`,
`semantic_index_state`, and finally `collections` (with `RETURNING
display_name` for the confirmation output). Any failure rolls back the whole
delete. No foreign-key cascade, trigger, or `PRAGMA foreign_keys = ON` is
relied upon; the PRAGMA remains a separate observation (OBS-011).

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Rely on `ON DELETE CASCADE` after enabling `PRAGMA foreign_keys = ON` | Virtual tables cannot declare foreign keys, so `passages` and `embeddings` would remain orphaned; the PRAGMA change is its own observation (OBS-011) |
| SQLite triggers to cascade deletes | Implicit cleanup is hard to audit and maintain; an explicit, enumerated delete list is deterministic and directly testable |
| Keep the status quo | Leaves permanent orphaned records and the rowid-inheritance corruption hazard (OBS-008) |

## Consequences

### Positive

- Complete cleanup is guaranteed by construction: every per-collection table
  is enumerated, so a schema addition without a matching delete clause is a
  visible test failure rather than silent orphaned data.
- Atomicity is provided by a single transaction; no partial destroy state is
  observable.
- The rowid-reuse hazard is eliminated: a recreated collection always starts
  clean.
- No new dependency, migration, or schema change.

### Negative Or Tradeoffs

- The delete list must be maintained as the schema grows (mitigated by the
  emptiness regression tests).
- The FTS5 rowid-subset delete must run before the `passage_files` rows are
  removed; the fixed statement order encodes this constraint.
- The database file's freed space is not reclaimed (no VACUUM), by decision
  (story OQ-001).

## Follow-Up Actions

- Implement the transactional multi-table delete in `destroy_collection`.
- Add store regression tests asserting SQL-level emptiness of all ten tables
  after destroy, atomicity on injected failure, rowid-reuse safety, and
  other-collection isolation.
- Revise `REQ-003` to state that destroy removes the collection and all of
  its data (R-SDD-05).
