# Architecture Decision Record

## Context

`mdsearch` must be delivered as a local-first Rust single binary. All collections
must live in one embedded database file per machine, and future slices must
support lexical, semantic, and entity-level contextual indexing in-process.
Collection creation also needs transactional persistence and reliable failure
recovery.

The project scale is 100 to 5,000 documents per collection, with search result
quality prioritized over indexing speed. The tool must work offline by default
and must not require a server component.

## Decision

Use Rust with SQLite as the embedded database and system of record for all
collections.

- Use one SQLite file for the default or explicitly selected database path.
- Use transactional relational tables for collection metadata and future entity relationships.
- Use SQLite FTS5 for the future lexical index.
- Use the `sqlite-vector` extension for future semantic vector storage and search in the same SQLite file.
- Use the Rust `fastembed` library to create local embeddings.
- Use the Rust `async-graphql` library as an internal in-process schema and query layer for contextual graph data stored in SQLite.
- Do not expose a GraphQL server or change the CLI-only product boundary through this decision.
- Package the selected SQLite integration and required extensions with the Rust binary.

This decision selects the database and local integration foundation without
finalizing the fastembed model, entity extraction model, or semantic-ranking
algorithm.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| SQLite with application-managed vector scoring | Does not use the selected `sqlite-vector` capability and shifts vector indexing and search responsibility into application code |
| Separate relational, vector, and graph databases | Violates the one-database-file constraint and complicates local installation |
| Vector-first embedded database | Does not provide as direct a fit for collection lifecycle, lexical search, metadata, and entity relationships |
| DuckDB | Better suited to analytical workloads than this transactional collection and update workflow |

## Consequences

### Positive

- Satisfies the single-file and embedded-operation constraints.
- Supports transactional collection creation and migrations.
- Provides a mature relational model for collections and entity relationships.
- Provides FTS5 as an in-process path for lexical search.
- Provides `sqlite-vector` as the in-process path for semantic vector search.
- Uses `fastembed` for local embedding generation in Rust.
- Provides `async-graphql` for internal contextual graph queries without requiring server mode.
- Keeps the initial binary free from a required external database service.
- Allows semantic and contextual data to remain in the same file.

### Negative Or Tradeoffs

- `sqlite-vector` extension packaging and compatibility must be validated for the final Rust binary.
- `fastembed` model assets must be distributed or provisioned locally without making runtime network access mandatory.
- `async-graphql` is a query layer, not graph storage; SQLite schema design remains necessary for entities and relationships.
- One file creates a single operational boundary; corruption or permission failures affect all collections in that file.
- Schema evolution must be managed carefully as all index types are added.

## Follow-Up Actions

- Prototype the collection schema and migration strategy for `US-001`.
- Validate the selected Rust SQLite integration, FTS5, and `sqlite-vector` availability in the single binary build.
- Validate offline embedding generation with `fastembed` and a selected local model.
- Define the SQLite entity/relationship schema and internal `async-graphql` context schema before EPIC-005.
- Benchmark vector storage and search at the PRD document scale before designing EPIC-004.
