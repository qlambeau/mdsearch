# Architecture Decision Record

## Context

`mdsearch embed` performs the embedding pass as an all-or-nothing batch: it
loads every passage of every targeted collection, embeds them all in one
blocking adapter call, then writes every vector row in one transaction
(OBS-016). At PRD scale (100–5,000 documents, 100–300 page files, CPU
inference) a rebuild runs many minutes with no terminal feedback — the user
cannot tell working from hung, and a mid-run failure wastes the run with no
partial signal.

The approved product decision (DEC-017, EPIC-012) requires visible progress:
per-file granularity, always on stderr, embedding phase only, with the stdout
report contract untouched.

## Decision

1. **Progress events from the use case.** The `EmbedCollections` use case emits
   progress events through a callback (`&mut dyn FnMut(EmbedProgress)`) with
   two kinds: `Files { collection, completed_files, total_files }` emitted
   after each file's passages are embedded, and `Writing { collection }`
   emitted before the vector write. The embedding generator port is unchanged:
   the use case groups the store-ordered passages by file and calls
   `generator.embed` once per file, preserving passage/vector alignment.

2. **Rendering in the CLI with `indicatif`.** The `app` crate renders the
   events with the `indicatif` crate (new dependency, owner-approved in this
   session): a `ProgressBar` drawn to stderr (`ProgressDrawTarget::stderr()`),
   message `embedding {collection}`, position = completed files, restarted per
   collection. A `Writing` event finalizes the bar and writes a single
   "writing semantic index for {collection}..." status line to stderr.
   Progress rendering is best-effort: a render failure never fails the run.

3. **stdout contract untouched.** Progress never appears on stdout; the
   per-collection outcome report is byte-identical (REQ-018 FR-004).

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Progress callback on the `EmbeddingGenerator` port | Churns the port contract and makes the adapter progress-aware; the use case already owns orchestration and knows file boundaries (R-SEP-03) |
| Line-per-file output | Noisy at PRD scale and pollutes scrollback; rejected by the owner in the story interview |
| TTY-detected progress (hidden when piped) | Rejected by the owner: progress is always on stderr, predictable for humans and harnesses alike |
| Hand-rolled `\r` single-line updates | Rejected by the owner: the `indicatif` crate gives a polished, maintained renderer for one small dependency |
| No progress at all | The approved DEC-017 product decision requires it |
| Per-passage or per-batch granularity | Files are the natural unit users think in; rejected in the story interview |

## Consequences

### Positive

- Visible, predictable feedback during long runs; users can estimate progress
  and detect hangs early.
- stdout output and the generator port contract are untouched; harness callers
  are unaffected.
- Progress is bounded: one update per completed file, never per passage.

### Negative Or Tradeoffs

- One new crate dependency (`indicatif` in `kv-app`), approved by the owner.
  The `0.18` line is used because `0.17` pulls the unmaintained
  `number_prefix` crate (RUSTSEC-2025-0119), which fails the `cargo deny`
  gate.
- The embedding phase issues one generator call per file instead of one call
  for the whole collection; inference dominates, so the per-call overhead is
  negligible, and passage order (and therefore pair alignment) is preserved.
- stderr volume grows with file count in non-TTY captures (plain line
  updates), which is inherent to always-on stderr progress.
