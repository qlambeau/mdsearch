# Architecture Decision Record

## Context

`PRD-001` identifies search result quality as the primary success metric for `mdsearch`, prioritizing it over indexing speed and query latency. However, `PRD-001` recorded Open Question `OQ-003`: *"How is search quality validated before release, given no golden set exists?"*

Existing academic information retrieval (IR) benchmarks (e.g., BEIR, MS MARCO, TREC) evaluate plain-text or web corpora. They do not match `mdsearch`'s target domain:
1. Markdown knowledge vaults featuring YAML frontmatter, hierarchical headings, wikilinks, and code blocks.
2. Passage-level retrieval with diff-style line range positions.
3. Multi-modal retrieval across lexical (FTS5 BM25), semantic (`fastembed` + `sqlite-vector`), and contextual entity graph links.

To validate retrieval quality quantitatively, prevent ranking regressions, and provide empirical criteria for tuning hybrid search fusion, `mdsearch` requires a dedicated evaluation methodology and ground truth dataset strategy.

## Decision

Adopt a self-contained, version-controlled **Search Quality Evaluation Framework** and **Golden Dataset Strategy** for `mdsearch`.

### 1. Golden Dataset Structure

The benchmark suite consists of three standard machine-readable JSONL files located in `tests/fixtures/eval/`:

- **Corpus (`corpus.jsonl`):** A representative test vault of Markdown documents containing varied lengths (100–5,000 document scale), frontmatter metadata, nested headings, wikilinks, and technical code blocks.
- **Queries (`queries.jsonl`):** A query dataset categorized across three retrieval modalities:
  - *Lexical / Keyword queries:* Exact symbols, CLI flags, file paths, and verbatim phrases.
  - *Semantic / Conceptual queries:* Natural language questions and conceptual paraphrases without direct keyword overlap.
  - *Contextual / Relational queries:* Queries spanning linked concepts and entity relationships.
- **Relevance Judgments (`qrels.jsonl`):** Ground truth mappings `(query_id, doc_id, line_start, line_end, score)` with graded relevance:
  - `0`: Irrelevant.
  - `1`: Relevant document (provides helpful context).
  - `2`: Exact target passage (directly answers or satisfies the query).

### 2. Dataset Construction Methodology (Hybrid Approach)

1. **Curated Golden Core (30–50 queries):** Hand-crafted by human developers from realistic vault scenarios, establishing ground truth with verified file and line range annotations.
2. **Synthetically Generated Suite (100–300 queries):** LLM-generated queries across chunked passages (generating paired factoid, conceptual, and multi-doc queries) to provide broad coverage.
3. **Hard Negatives Suite (20–30 queries):** Queries with high lexical overlap to non-relevant sections to guard against keyword distraction and false positives.

### 3. Quantitative Evaluation Metrics & Target Baselines

Evaluate retrieval quality against the top-$K$ passages (default $K=5$, matching agent prompt context injection limits):

- **Recall@5 / HitRate@5:** Proportion of queries where at least one grade $\ge 1$ passage is returned in the top 5 results (Target: $\ge 0.85$).
- **MRR@5 (Mean Reciprocal Rank):** Rank position of the first relevant passage (Target: $\ge 0.70$).
- **NDCG@5 (Normalized Discounted Cumulative Gain):** Quality of ranking order accounting for graded relevance (Target: $\ge 0.75$).

### 4. Tooling & Automation

- Implement an offline evaluation runner in `xtask` (`cargo xtask eval`).
- The evaluation command will:
  1. Ingest and index the evaluation fixture corpus into an isolated SQLite database.
  2. Execute all queries against the current `mdsearch` engine (lexical, semantic, or hybrid mode).
  3. Compute Recall@5, MRR@5, and NDCG@5 against `qrels.jsonl`.
  4. Output a summary report and fail CI if regression thresholds are breached.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Use standard academic benchmarks (BEIR / MS MARCO) | Plain-text datasets lack Markdown structure, frontmatter, wikilinks, and line-level passage targets. |
| Rely solely on manual ad-hoc testing | Subjective, non-reproducible, and incapable of detecting ranking regressions during algorithmic tuning. |
| Purely synthetic evaluation dataset | High volume but risks synthetic bias or unrealistic query distributions if not anchored by a human-curated core. |
| Defer evaluation until after all search epics are implemented | Prevents data-driven tuning of `fastembed` model selection (EPIC-004) and hybrid fusion weights. |

## Consequences

### Positive

- Resolves `PRD-001` Open Question `OQ-003` with a concrete, reproducible verification framework.
- Provides empirical metrics (Recall@5, MRR@5, NDCG@5) to guide model selection, chunking parameters, and hybrid rank fusion.
- Protects against retrieval regressions across CLI releases.
- Remains local-first and fully offline, running within the existing `cargo xtask` workflow.

### Negative Or Tradeoffs

- Requires ongoing maintenance of fixture files and relevance judgments when schema or chunking strategies evolve.
- Running full evaluation runs adds execution time to release verification gates.
