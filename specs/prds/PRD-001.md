# Product Requirements Document

## 1. Vision And Problem

### Vision

A self-contained CLI search engine that turns a developer's markdown knowledge
vault into a queryable local database: collections of files get lexical,
semantic, and entity-level contextual indexes, and both humans and coding agent
harnesses can retrieve ranked passages or full documents to ground LLM context
(RAG).

### Problem Statement

Developers building LLM-wiki-style markdown vaults have no lightweight,
embeddable, local search engine for them. Generic search (grep, basic FTS) is
lexical-only; full RAG stacks require server components, vector databases, and
indexing pipelines. A coding agent harness that wants to fill its context window
from a vault needs a single-binary tool that indexes once and answers lexical or
hybrid (lexical + semantic) queries, optionally enriched with the surrounding
entity context, with provenance.

### Why Now

The vault is already built and local tooling exists that proves the pattern;
what is missing is a reusable CLI that embeds the database and all three index
types in one file, callable from agent harnesses.

## 2. Target Personas And Journeys

| Persona | Need | Relevant journey |
| --- | --- | --- |
| Developer-curator (human) | Build and maintain a searchable collection from markdown files; find knowledge quickly | Creates a named collection, adds files, runs update, searches lexically or hybrid, reads ranked passages with diff-style positions, opens a full file by name or ID |
| Coding agent harness (programmatic) | Fill LLM context with grounded passages from the vault | Invokes the binary via CLI switches, receives richer JSON results (passages, provenance, entity links), injects top-K into the LLM prompt |

## 4. Functional Scope And Epics

### In Scope

| Epic ID | Epic | Outcome |
| --- | --- | --- |
| EPIC-001 | Collection management | User creates named collections, lists all collections, and destroys a collection; all collections live in one database file per machine |
| EPIC-002 | Ingestion and incremental indexing | User adds markdown files to a collection; an update command re-indexes one or all collections when files are added, modified, or deleted; file content and IDs are managed by the embedded database |
| EPIC-003 | Lexical indexing and search | The engine builds a lexical (BM25-style) index; a dedicated lexical search command returns ranked passages |
| EPIC-004 | Semantic indexing and hybrid search | The engine builds a semantic (vector) index; a hybrid search command fuses lexical and semantic results into one ranked list |
| EPIC-005 | Contextual entity indexing | The engine builds an entity-level graph (entities as nodes, relationships as edges) extracted from the collection; retrieval can surface links to related concepts |
| EPIC-006 | Retrieval and output | Queries return ranked passages with diff-style positions in the file by default; a switch selects machine-readable JSON that is richer than the human format; a command retrieves a complete file by name or by its indexing-assigned ID; a switch shows or hides related-concept links |

### Capability Boundaries

- All three index types (lexical, semantic, contextual) are produced from the
  same ingestion pipeline and stored in the same database file.
- Retrieval is configuration-driven: output format, related-concept links, and
  external-service usage are controlled by command-line switches, with local
  operation as the default.

## 5. Non-Functional Requirements

| Requirement | Target or constraint | Rationale |
| --- | --- | --- |
| Local-first operation | All indexing and search works fully offline by default | Developer vaults may be private; no network dependency |
| External services | Opt-in only, via CLI switches | Allow better models when the user chooses |
| Delivery | Single compiled binary, Rust ecosystem | Easy install and harness invocation |
| Embedded database | Single database file holding all collections; engine must support lexical, semantic, and contextual search in-process | Portability, zero server components |
| Scale | 100-5,000 documents per collection; short-to-medium files typical, up to 100-300 page documents possible | Defines architecture choices |
| Quality | Search result quality is the top priority | Core value of the tool |
| Latency | Query speed second priority; soft targets (TBD) | Harness context-filling is latency-sensitive |
| Machine consumption | JSON output mode selectable by switch; richer than the human display | Harness integration |

## 6. Assumptions And Out Of Scope

### Assumptions

- File IDs are assigned during indexing and are stable enough to retrieve a file
  by ID.
- Frontmatter metadata (title, tags, aliases, summary) is indexed alongside body
  content, LLM-wiki-style.
- The database file is the source of truth for collection content; original
  markdown files remain the user's on-disk source.
- One database file per machine contains all collections.
- The context graph is entity-level: nodes are entities (concepts, people,
  topics), edges are relationships between them.

### Out Of Scope

- Answer generation - the tool retrieves only; the harness/LLM synthesizes
- File watching - indexing is driven by explicit update commands
- Multi-user, auth, permissions
- Web UI or server mode
- Cloud sync or hosted collections
